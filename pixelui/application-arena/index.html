Fixed Application Arena / 固定 App 内存区

Fixed Application Arena / 固定 App 内存区
文档首页 快速开始 架构 生命周期 GitHub
中文English

PixelUI 现已完全杜绝动态内存。ViewManager 内部的 ApplicationStack 保留一块固定字节区，所有活着的 App 按页面栈顺序原地构造在里面。

*App A 和 App B 只占用各自实际需要的字节，中间的 pad 由对齐要求决定。对象字节与 metadata 分开：metadata 记录回滚位置和具体析构函数。

Arena 字节数、最大对齐和页面深度都是固定配置，集中列在资源上限。

内存布局

每次 push 先按 alignof(T) 对齐当前 offset，检查对齐填充加对象字节是否超过 arena，然后 placement-construct。只有构造成功后才提交 metadata。pop 通过具体类型的 destroy thunk 调用正确析构函数，并恢复上一个 marker。

为什么用 LIFO arena

  • 容量和失败可预测；
  • 没有 App 对象的堆碎片；
  • 小 App 只使用自己需要的字节，不用每个槽都按最大 App 预留；
  • 和页面栈一样是 LIFO，回收不需要通用 allocator。

这意味着只能销毁栈顶 App，不支持从中间抽掉一页。这对于绝大多数应用而言足以。

Factory 与自定义构造

launch() 使用 AppItem 中的 factory 在 arena 内构造具体类型。常规注册见启动 AppLauncher；特殊构造参数可以使用无捕获 thunk：

thunk 只能在 storage 中构造一个声明的具体类型，或者在什么都没构造时返回 null。

实测和目标平台

Apple arm64 Debug 对 v0.3.1-beta 的一次测量为：ApplicationStack=4416、ViewManager=4608、PixelUI=9216 字节；其中 arena 本身是 4096 字节。这不是对 MCU ABI 的保证，请在实际编译器上重新测量。
